Olivia Carter's first Windows Autopilot deployment reached the Windows desktop. Company Portal opened, recognised her device, and reported that it could access company resources. The next job is to prove that **the device, user, management platform and applications agree**.

For this validation exercise, we'll distinguish three kinds of result:

- **Verified in Intune or Autopilot:** directly shown by an administrative report.
- **Verified on the endpoint:** confirmed by inspecting the running Windows VM.
- **Still to verify:** needs another device or portal check before we call the entire security posture validated.

This isn't just paperwork. The evidence becomes our reference point before BitLocker, Defender, compliance and Conditional Access are introduced.

### 1. Identify the workstation correctly

Our test machine has two names with different purposes:

| Reference | Value | Meaning |
|---|---|---|
| Asset and Oracle VirtualBox VM | `WF-LT-001` | Internal lab asset identifier |
| Windows hostname | `DESKTOP-QDSCPUK` | Name generated by Windows because the Autopilot device-name template was disabled |
| Intended employee | Olivia Carter | Finance Analyst, standard pilot account |
| Autopilot classification | `CORPORATE` | Group Tag used for the corporate device deployment |
| Autopilot profile | `WF_AP_CORPORATE_USER_DRIVEN` | User-driven, Microsoft Entra joined deployment |

Search for `DESKTOP-QDSCPUK` in the Windows managed-device list. Do **not** expect the Intune display name to be `WF-LT-001`.

### 2. Check the Windows Autopilot registration

In the [Microsoft Intune admin center](https://intune.microsoft.com/), open:

**Devices → Device onboarding → Enrollment → Windows Autopilot → Devices**

Select the record for the VirtualBox device and inspect its Group Tag and profile assignment.

![VirtualBox Autopilot record showing the CORPORATE group tag and assigned profile]({{ '/assets/images/endpoint-management/wf-autopilot-profile-assigned.png' | relative_url }})

**Verified:** The registered device is still recognised by Windows Autopilot, and its profile assignment is **Assigned**.

**Still to verify on the individual record:** The updated **enrollment status**, exact assigned profile name, and **associated Intune device** after Olivia completed OOBE. The screenshot of the list does not show these post-enrollment fields, so don't treat it as proof of that association.

### 3. Verify the Intune managed-device record

Navigate to **Intune → Devices → All devices**, then find `DESKTOP-QDSCPUK`. Inspect the managed-device record.

![Intune Windows device list showing corporate ownership, management, compliance label and Olivia as primary user]({{ '/assets/images/endpoint-management/wf-intune-managed-device.png' | relative_url }})

The screenshot confirms:

| Field | Observed evidence |
|---|---|
| Managed by | **Intune** |
| Ownership | **Corporate** |
| Primary user | **Olivia Carter** |
| Operating system | **Windows** |
| Compliance label | **Compliant** — meaning requires further interpretation |
| Last check-in | A value is visible but truncated; its currency must be checked in the full record |

**Important:** A row labelled **Compliant** is not evidence that BitLocker, Defender for Endpoint, security baselines or a custom compliance policy have already been deployed. Intune can treat devices with no applicable compliance policy as compliant, depending on the tenant setting. We'll assess this separately during compliance implementation.

Before pushing endpoint-security policies, open the device's full **Overview / Properties** and verify that its **last check-in is current**. If the VM was powered off after the pilot, start it, connect to the internet and initiate an Intune sync as appropriate.

### 4. Verify Company Portal installation

Open **Intune → Apps → All apps** (or **Apps → Windows → Windows apps**, depending on your portal view). Select **Company Portal**.

![Company Portal Intune app overview showing one installed device and no install failures]({{ '/assets/images/endpoint-management/wf-company-portal-installed-summary.png' | relative_url }})

Then choose **Monitor → Device install status**.

![Company Portal per-device installation report for DESKTOP-QDSCPUK]({{ '/assets/images/endpoint-management/wf-company-portal-device-install.png' | relative_url }})

**Verified:** Company Portal installed on Olivia's endpoint and is reported as installed in Intune. This also agrees with the working Company Portal interface observed during Lesson 8.

### 5. Confirm the Microsoft 365 Apps baseline

Our required user-targeted package is:

`Microsoft 365 Apps - Wire Finance Pilot`

Open the Windows application catalogue in Intune and locate it alongside Company Portal.

![Intune Windows apps catalogue listing Company Portal and Microsoft 365 Apps Wire Finance Pilot]({{ '/assets/images/endpoint-management/wf-intune-windows-apps.png' | relative_url }})

On the Windows endpoint, inspect the actual application availability. The selected Word, Excel, PowerPoint, Outlook, OneNote and Teams applications were **confirmed present on the pilot VM** after the initial pending state recorded in Lesson 8.

For a corresponding administrative report, open:

**Apps → All apps → Microsoft 365 Apps - Wire Finance Pilot → Monitor → Device install status / User install status**

Check Olivia's row and confirm that Intune reports **Installed** rather than **Pending** or **Failed**. This final application-report screenshot hasn't been collected yet; don't invent it.

#### Why the Company Portal app catalogue is empty

On the employee's machine, Company Portal may show no optional applications available for installation. This is **expected with our current assignments**:

| Application | Assignment | User experience |
|---|---|---|
| Company Portal | **Required** — `SG-DEVICES-AUTOPILOT-CORPORATE` | Installed automatically |
| Microsoft 365 Apps | **Required** — `SG-PILOT-IDENTITY` | Installed automatically for the pilot user |
| Optional self-service apps | **None assigned as Available** | Empty **Available apps** catalogue |

An empty self-service catalogue **does not mean** those Required apps were not pushed. To populate the employee catalogue in a later lesson, assign appropriate software as **Available** to the intended users. Don't switch essential Required deployments to Available just to make them visible.

### 6. Validate the Microsoft Entra device join

We have strong evidence that the machine completed user-driven enrollment and is managed by Intune. However, the supplied screenshots do not directly display the **Microsoft Entra join type** or a matching Entra **Device ID**.

For the final identity check, sign in to the VM, open Command Prompt and run:

```cmd
dsregcmd /status
```

Under **Device State**, confirm the cloud-only model:

```text
AzureAdJoined : YES
DomainJoined  : NO
```

Then open **Microsoft Entra admin center → Entra ID → Devices → All devices**. Find `DESKTOP-QDSCPUK` and verify **Join type: Microsoft Entra joined**, **Enabled: Yes**, and its Device ID. Match this with the ID shown by `dsregcmd /status` rather than relying only on the display name.

Capture a redacted verification screenshot once checked. The earlier Autopilot group-membership screenshot is not a substitute for this evidence.

That is sufficient to move into **preparing** the endpoint-security baseline, provided the device is online and its management record is healthy. Before formally closing the full Lesson 9 validation checklist, capture the remaining join, association, current check-in and final Office reporting details above.

### Next: Build the Windows security baseline

Our architecture reserves modular security policies for the pilot device group `SG-DEVICES-WINDOWS-PILOT`: BitLocker, Defender Antivirus, Windows Firewall, attack-surface reduction, Defender for Endpoint onboarding, and additional baseline/account hardening. We'll apply and verify these **one control at a time**, document each confirmed outcome, and only later expand targeting to the corporate population.

Before creating `WF-SEC-WIN-BITLOCKER`, verify TPM readiness, Secure Boot, recovery environment, the current encryption state and a safe recovery-key strategy for this VirtualBox VM. A device showing **Compliant** in today's Intune list is not a substitute for those checks.
