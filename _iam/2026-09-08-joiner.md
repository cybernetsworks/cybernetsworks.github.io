A new employee is joining Wire Finance.

At first, onboarding might sound simple:

**create an account and give them access.**

But that raises several questions.

Who confirms who the employee is?

Who decides what they need?

Which access comes automatically from their department or role?

What happens if they require sensitive or privileged permissions?

And who confirms everything is ready before they begin work?

The **Joiner process** gives Wire Finance a repeatable way to answer those questions.

#### The Joiner Process

![Wire Finance Joiner Process]({{ '/assets/images/active-directory/joiner_process.png' | relative_url }})

The flow shows something important:

**identity creation does not happen first.**

Before IT creates the account, Wire Finance establishes who the employee is, what role they will perform, which baseline applies, and whether any additional access requires approval.

Only then does the technical onboarding begin.

##### From Employee Information to Access

HR provides the authoritative employment information.

The manager then confirms the employee's role and responsibilities.

That allows Wire Finance to connect the new starter to the access model we designed earlier.

For example, if Olivia Carter joins as a Finance Analyst:

```text
Olivia Carter
      │
      ▼
WF-BASE-001
      +
Finance Department Baseline
      +
Finance Analyst Role Baseline
```

We are not deciding Olivia's permissions from scratch.

Her position in the organisation tells us which normal access baselines should apply.

If she needs access beyond those baselines, that requirement follows a separate approval path.

##### Who Provides What?

The Joiner process depends on several teams providing or validating different pieces of information.

| Information / Decision | Provider / Owner |
|---|---|
| **Legal name** | HR |
| **Preferred name** | Employer / HR |
| **Job title** | HR |
| **Department** | HR |
| **Manager** | HR |
| **Employment type** | HR |
| **Start date** | HR |
| **Work location** | HR |
| **Staff role / function** | Hiring manager |
| **Required applications** | Manager + application owner |
| **Required data access** | Manager + data owner |
| **Privileged access** | Manager + Security / IT approval |
| **Device type** | Manager + IT / Deployment |
| **Licence requirement** | IT based on role / application needs |
| **Department groups** | IT based on approved role |
| **Security groups** | IT / Security |
| **MFA / Passwordless registration** | User, enforced by IT / Security |
| **Account creation** | IT / Identity team |
| **Device provisioning** | Deployment / Endpoint team |
| **Final access validation** | Manager + IT |
| **Security monitoring** | SOC |

The table reinforces that onboarding is not owned by one person or one team.

HR provides employment facts.

Managers provide business context.

Application and data owners approve access to the resources they are responsible for.

Security becomes involved where sensitive or privileged access is required.

IT and Identity turn those approved decisions into a working technical identity.

##### Normal Access and Additional Access

The Joiner process also preserves the boundaries we established earlier.

Normal access can be derived from:

```text
Company Baseline
      ↓
Department Baseline
      ↓
Role Baseline
```

But sensitive or privileged requirements do not simply get bundled into onboarding.

They still require the appropriate approval.

This means joining Wire Finance does not automatically justify every permission someone might eventually need.

The goal is to provide **the access required for the role — not the most access possible.**

##### Ready to Work

Creating the identity is only one part of onboarding.

The process also makes sure that:

- Groups and licences are assigned
- The employee's device is provisioned
- Authentication is registered
- Access is validated
- The manager confirms readiness

Only then does the employee begin work.

That makes the end of the Joiner process more meaningful than simply:

**Account created.**

The real outcome is:

**the right person has the right identity, the right access, the right device, and a working authentication path before they begin their role.**

But that access will not necessarily remain correct forever.

Employees change departments.

They receive promotions.

Their responsibilities change.

And sometimes they need permissions they did not require when they first joined.

So the next lifecycle problem is not creating access.

It is **changing it without allowing old access to follow the employee forever.**
